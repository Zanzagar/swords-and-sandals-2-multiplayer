### A — no locked definition contains both types — recommended

`D^{SB}_{locked,v}` is empty. Every locked definition's qualifying one-
coordinate edges support exactly one type, while C112-C requires at least one
state-supporting name and a distinct boundary-supporting name. This gives every
named Relic one learnable comparison dialect and extends the selected
definition-pure design vocabulary.

Costs are a forced name taxonomy, at least two locked definitions, no within-
name cross-axis puzzle, and possible rarity or power caste between the two
dialects. “State-supporting only” does not mean boundaries never differ;
diagonal pairs may still differ in both coordinates. Tight floors are
`7/15/90`.

### B — dual-type and single-type definitions coexist

`D^{SB}_{locked,v}` is nonempty and proper. At least one name contains a pair
of each type and at least one other name supports only one type. This is the
strongest gameplay countercase if dual-type names are disclosed, accessible,
non-dominated advanced sidegrades beside simpler teaching names.

Without those later safeguards B creates the largest hidden taxonomy, token-
dual-pair risk, and a premium or “complete Relic” reading. The single-type
complement may all support the same type; B does not require both singleton
classes. Tight floors are `7/15/90`.

### C — every locked definition contains both types

`D^{SB}_{locked,v}=D^{U=}_{locked,v}`. Every locked name contains at least one
pair of each type. C closes name-level type segregation but imposes two teaching
and validation languages on every name, risks homogenization, and can be
satisfied by obscure pairs on different or inaccessible instances. It does not
give both types to one instance, fiber, key, endpoint, or artifact. Tight floors
remain `6/11/66`.
